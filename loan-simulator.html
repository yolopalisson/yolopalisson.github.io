Loan Eligibility Simulator

A responsive, production-grade loan simulator that gives customers instant eligibility feedback, built with React, TypeScript, and an accessibility-first mindset.

Start the walkthrough →
01 · The Brief

What was asked

Create a responsive UI where customers input their income, expenses, and desired loan amount to see estimated eligibility results using mocked data.

◆ Requirements

  • Responsive UI
  • Input: income, expenses, loan amount
  • Estimated eligibility results
  • Mocked data

✦ Additional Standards

  • Production-grade quality
  • Runnable Dockerfile
  • README explaining build, run, test
  • Use the supplied API spec

02 · Deliverable

What I built

A full loan application flow; from input to amortisation schedule, consuming all four endpoints from the spec.

📝 Input Form

Personal info, financial info, and loan details across three clear fieldsets.

✓ Live Validation

Rules fetched from the API and enforced with Zod. Inline errors plus an accessible error summary.

📊 Eligibility Verdict

Approval likelihood, risk category, and a decision reason, all rendered on a summary card.

💰 Recommended Loan

Recommended amount, interest rate, monthly repayment, and total cost over the term.

📈 Affordability

Disposable income, DTI, LTI, and an affordability score, visualised with progress bars.

📅 Payment Schedule

Full month-by-month amortisation. Table on desktop, cards on mobile. Expandable.


03 · Design

Architecture

Three clean layers. A real backend swaps in by changing one line.

Layer 1
UI
React · Tailwind · RHF + Zod
Layer 2
State
TanStack Query · caching · loading · errors
Layer 3
API
Fetch client · MSW mock handlers

Why it matters: The UI never knows whether the API is real or mocked. Swapping to Capitec's backend is a URL change in src/api/loans.ts.

05 · Engine

The calculation engine

Where the app becomes financial software.

∑ Amortisation

Standard formula for fixed-rate repayment. Generates a full month-by-month schedule tracking principal, interest, and remaining balance.

⚖ Eligibility Rules

Approval requires positive disposable income, DTI ≤ 40%, requested amount ≤ max eligible, and credit score ≥ 600.

% Ratios

DTI = existing debt ÷ monthly income. LTI = max eligible amount ÷ annual income.

⚠ Documented Assumptions

The spec's example response had internal inconsistencies. I documented every interpretation in the README and covered it with unit tests.

08 · Ship

Deployment pipeline

Local → GitHub → Vercel → Live URL.

  • Dockerfile — multi-stage build, Nginx runtime, SPA fallback
  • vercel.json — SPA rewrites so client-side routing works on refresh
  • VITE_ENABLE_MSW=true — env var that activates MSW in production builds
  • .gitignore — excludes node_modules, dist, env files
  • Auto-deploy — every push to main triggers a Vercel rebuild

09 · Reasoning

Key decisions & why

◈ MSW, not hardcoded data

Exercises the real network layer. Testable. Swaps to a real backend in one line.

◈ API-driven validation

Business rules live in one place. Backend changes ripple forward automatically.

◈ Documented assumptions

The spec had ambiguities. I made explicit choices and tested them, instead of guessing silently.

◈ Accessibility first

Not bolted on. Every component was designed with keyboard and screen readers in mind.
